# X 管家重新对接计划与协作清单

> 更新日期：2026-09-01
> 状态：最高优先级，旧采集链路与旧抓取结果不可复用。

## 1. 边界与安全原则

1. 新采集系统与门店、员工、岗位、排班、成本等业务表物理隔离。
2. 原始响应只追加或版本化保存，采集任务不得直接修改经营事实。
3. 原始数据必须经过完整性校验、标准化、去重、关联、业务校验和人工发布后，才能进入经营事实层。
4. 同步失败、登录失效、分页缺失或规则异常不得清空、覆盖现有业务数据。
5. 自动同步默认关闭；先以固定门店、固定日期窗口手工执行。
6. 旧 `web-data-platform`、V1 Bridge 和历史抓取记录仅用于排查已知问题，不作为正确数据或正式实现来源。
7. 凭证、Cookie、Token、HAR 等敏感材料不得写入 Git、开发记录或普通日志。

## 2. 对接模块顺序

1. 账号登录、会话续期、门店列表。
2. 综合收支。
3. 充值明细与充值汇总。
4. 团购核销与撤销。
5. 商品销售与退款。
6. 上机、网费与结算。
7. 交班数据和班次归属：优先同步本班总收入、网费收入、商品销售，并保留交班时间和本班起止时间。
8. 数据完整性、断点续采、补采和监控。
9. 标准事件、经营事实发布与页面接入。

### 2.1 第一阶段经营数据合并口径

- 正式日快照来自“财务 → 财务营收报表 → 综合收支报表”，每日采集各门店前一完整自然日数据。
- 今日临时快照来自“财务 → 经营数据表 → 账目汇总”，仅保存每个门店今日最新一份，目标刷新周期为 2 分钟。
- 当月展示值 = 当月已结算日快照合计 + 今日最新临时快照；临时快照不是累计流水，每次刷新必须覆盖同店同日旧值。
- 次日正式日快照采集成功后，昨日临时快照自然退出月度查询；不得把临时值再次累加到正式快照，避免重复计算。
- 正式采集失败时保留上一批已发布数据，并明确标记缺失日期；禁止用临时数据冒充已经结算的历史日数据。
- 两张报表字段不同：综合收支以盈余为总额并展示网费、商品、租赁、权益和其他收支分类；账目汇总以小计为总额，并增加钱款来源和终端来源。月度核心营收映射为“历史日盈余 + 今日小计”，分类字段必须逐项核对后合并。

## 3. 每个模块必须建立的数据合同

每个接口必须记录：

- 页面入口、接口 URL、HTTP 方法和调用顺序。
- 必要请求头、Cookie 类型和会话依赖，不保存真实敏感值。
- 门店参数、时间参数、营业日边界和时区。
- 分页参数、每页数量、总数和结束条件。
- 明细唯一键、业务唯一键和更新标识。
- 金额、数量、发生时间、结算时间和更新时间字段。
- 状态、退款、撤销、冲正和作废含义。
- 返回值是明细、快照还是汇总。
- 与其他模块可能重复的业务关系。
- 同条件页面合计、Excel 合计和接口合计。

3. 页面筛选条件和合计截图。

首个样本建议使用 9 店 `AQXH-4624`，固定一天和固定一个营业日窗口分别验证。

### 4.3 HAR 导出要求

- 使用浏览器开发者工具 Network。
- 开启 Preserve log/保留日志。
- 清空旧请求后再执行一次完整查询。
- 从进入模块、选择门店和时间，到翻页/导出结束，全程保留。
- 使用“Save all as HAR with content”。
- HAR 可能包含登录凭证，应只通过本地文件交给开发，不上传公共网盘或提交 Git。
