## 1. 本次重构的核心目标

V2 不再以“修正某家门店的最终金额”为中心，而是建立一套可解释、可追溯、可复算的数据系统：

1. X 管家是主要经营数据源，门店系统的统计结果应能与 X 管家同口径报表对齐。
2. 所有原始记录先完整保存，再进行标准化、去重、关联、分类和指标计算。
3. 每个最终金额都能下钻到来源接口、原始记录、过滤原因和计算规则。
4. 不针对门店硬编码差额，也不使用运营手工值覆盖同步数据。
5. V1 暂时保留运行，V2 并行建设和对账，验收通过后再逐步切换。

## 4. 已确认的业务需求

### 4.1 岗位

- 系统维护默认岗位模板。
- 门店可以继承系统默认岗位。
- 门店可以在继承后新增自己的岗位。
- 员工关联门店岗位，岗位后续承载权限、排班和评价规则。

### 4.2 门店资料与经营档案

门店资料页不仅保存基础信息，还需形成门店经营档案，包括：

- 基础资料和经营状态。
- 固定成本、变动成本及其配置规则。
- 盈亏走势、同期/环期对比、预估经营盈亏。
- 开店基础投入、累计基础成本开支、回本金额和回本周期。
- 设备区域、设备配置、采购价格、采购日期、预估换汰周期。
- 可手动刷新硬件市场参考成本，并估算本店升级成本。

### 4.3 员工

- 员工资料、登录账号、所属门店和岗位。
- 入职、在职、离职等状态及时间线。
- 排班、排岗、临时调班。
- 班次业绩、员工评级、综合评分和排名展示。
- 个人业绩第一阶段仍按班次归属：同一班次的员工看到同一班次业绩。
- 提点功能只预留扩展入口，未来可能受门店评级、员工评级、提点基数和业绩类别影响。

### 4.4 业绩目标和动态拆分

- 利润目标支持绝对值和预期目标两种方式。
- 预期目标根据历史利润及增长百分比推算；无历史数据时允许手工录入启动数据。
- 网费、商品等目标支持历史数据比例和用户固定比例两种生成模式。
- 主营业务暂按整体 90% 作为计算中的 100%；剩余无法归入主营的收入统一列为“其他”。
- 充值、团购计入主营业务。
- 成本中的材料、福利、工资、管理费通过比例/公式计算，不直接固化金额。
- 当前工资口径：总成本减去能通过业绩预算计算出的费用，余额视为工资。
- 门店管理费可配置，9% 为兜底比例。
- 月目标总额固定，不因实际进度而改变；只动态重算未结束日期/班次的剩余目标。
- 已结束班次锁定；班次完成并取得截止数据后实时触发重算。
- 示例：月目标 30 万，1 日完成 1.2 万，则后续日目标为 `(30万 - 1.2万) / 29`。
- 同一天白班目标 5,000，若实际 4,000，晚班目标调整为 6,000；若实际 6,000，晚班目标调整为 4,000。
- 另行展示按当前速度预测的月底完成额和预测达成率，但预测不得修改月目标。
- 员工请假、调班、离职不改变已产生班次数据，业绩只与班次绑定。
- 员工任务系统暂缓。

## 5. 数据准确性的基本原则

正确链路应为：

`X 管家原始响应 → 原始数据层 → 标准业务事件层 → 去重/关联层 → 指标事实层 → 展示与对账`

### 5.1 原始数据层

每次抓取至少保留：

- 来源系统、接口、请求参数和响应原文。
- X 门店 ID、门店名称、业务记录 ID。
- 抓取时间、业务发生时间、结算时间、更新时间。
- 数据状态、页码/游标、请求批次号。
- 原始记录内容哈希。

原始记录只追加或版本化保存，不因后续规则变化而丢失。

### 5.2 标准业务事件层

将不同报表转换为明确事件，例如：

- `RECHARGE_PRINCIPAL`：充值本金。
- `RECHARGE_DIRECT_REWARD`：充值直接赠送。
- `MARKETING_CREDIT`：营销活动虚拟赠送，不一定计业绩。
- `PRODUCT_SALE` / `PRODUCT_REFUND`：商品销售/退款。
- `OTA_REDEEM` / `OTA_REVERSE`：团购核销/撤销。
- `NET_FEE_SETTLEMENT`：网费结算。
- `LEASE_INCOME`：租赁收入。
- `OTHER_INCOME`：其他收入。

每个事件必须保留来源记录 ID 和转换规则版本。

### 5.3 去重与跨来源关联

- 同一来源优先使用业务主键去重，业务主键缺失时才使用稳定组合键。
- 分页重复、任务重跑、更新后的同一记录不得重复累计。
- 不同来源的数据不能仅因金额相同就删除。
- 充值、团购、综合报表、交班报表之间先做业务关联，再判断哪个是事实、哪个只是汇总或参考。
- 所有过滤规则必须记录规则编号和原因，支持查看“为什么未计入”。

### 5.4 时间口径

必须同时区分：

- 自然日/月。
- 营业日（目前验证经常使用 09:00 至次日 09:00）。
- 班次开始/结束时间。
- 发生时间、结算时间、更新时间。

禁止用抓取时间代替业务归属时间。页面必须展示数据截止时间和最近同步时间。

### 5.5 状态与会话监控

- 主营数据会话与商品销售平台独立凭证要分别检测。
- 商品接口可能依赖独立 Cookie/PHPSESSID，不能用主营会话正常推断商品会话正常。
- 顶部告警应明确指出失效的数据域、受影响门店、最后成功时间和恢复动作。
- 恢复后应提供明显的“重新检测/立即同步”入口，并自动补采缺失时间段。

每份数据合同需确认：接口、请求参数、分页方式、门店字段、唯一键、金额字段、状态字段、发生/结算/更新时间、退款方式、是否为明细或汇总、是否可能与其他模块重复。

- 实现原始数据入库、幂等采集、分页完整性校验。

- 展示 X 管家总计、系统计入、系统排除和差额。

- 支持按门店、日期、班次、业务类别查看。
- 展示最近成功同步、数据截止时间、断档区间和补采状态。

- 岗位模板及继承。

### 阶段 5：经营分析与业绩目标

- 损益、趋势、对比、预测和回本周期。

- 日/班次目标拆分及实时重算。
- 班次和员工视角展示。

### 阶段 6：并行验证与切换

## 11. 关键验收标准

- 幂等：同一批数据重复同步不会增加金额。
- 完整：分页和时间窗口无缺页、无断档。
- 可解释：任何指标都能追溯到原始记录。
- 可复算：修改规则后可按版本重算指定门店/时间段。
- 可对账：差异不是只显示金额，而是列出造成差异的记录。
- 可监控：断线、凭证失效、同步延迟和补采失败均有明确告警。
- 时间一致：页面明确展示营业口径、数据截止时间和最近同步时间。
- 试点门店误差目标：先达到绝对差额可逐条解释，再以业务认可的容差作为上线门槛；不得用硬编码差额达标。
