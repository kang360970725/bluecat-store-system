# 员工小程序 Wi-Fi 考勤试点

`apps/employee-mini` 是早期微信原生预览工程；当前真机工程是仓库同级的 `employee-mini-taro`。用试点小程序 AppID 在微信开发者工具中导入其 `dist` 目录。API 使用已加入小程序 request 域名白名单且以 `/api` 结尾的 HTTPS 地址，AppSecret 只配置在服务端。

员工端采用独立微信小程序。当前原生工程作为试点预览，后续 Taro 实现按[独立小程序方案](employee-mini-taro-plan.md)推进。

## 测试环境准备

1. 在隔离测试库应用新增 Prisma 迁移。准备营业中门店、已发布或已锁定的排班，以及已改初始密码的在职员工账号。
2. 参考 `.env.example` 配置 AppID、AppSecret、批准的提前上班打卡分钟数和延后下班打卡分钟数。夜班使用排班日和跨夜标记。窗口只控制打卡准入，不用于迟到、早退或工资判定。
3. 持有该店 `schedule:update` 权限的店长或管理员进入「门店中心 → 门店工作台 → 排班与考勤」，登记路由器或接入点的 BSSID（硬件 MAC），一个门店可配置多个。
4. 员工绑定现有员工账号，连接门店指定 Wi-Fi，再对已发布或锁定的正常班或加班班次选择上班/下班打卡。小程序读取当前 BSSID 并连同微信身份提交；服务端核对员工、门店、排班、时间窗口和 BSSID。员工密码、微信会话密钥不写入本地存储。

## 补卡审批

员工可选历史排班日期，对缺少的上班卡或下班卡填写实际时间和原因。总部 V2 超级管理员或获得指定门店审批权限的人员在「员工考勤 → 补卡审批」处理待办。审核必须填写说明，禁止自审。补卡通过后新增一条有审批来源的记录；正常 Wi-Fi 打卡先到时关闭同类待审申请。每个班次分别保留至多一条上班卡和一条下班卡。

## Web 端考勤查询和授权

「员工考勤 → 考勤记录」按北京时间排班日、门店查询，分别显示 Wi-Fi、历史扫码、补卡或暂无记录。角色管理中可按需授予 `attendance:view`（查看考勤）、`attendance:review`（审批补卡）和 `attendance:export`（导出月度考勤）；迁移只登记权限点。员工岗位授予的权限随对应门店生效，并受账号门店范围限制。没有门店归属的总部岗位按账号的指定门店或全部门店范围生效。超级管理员仍可跨店管理。授权后重新登录可刷新菜单，接口每次读取当前授权。

## 现场验收

- 用 iPhone 和 Android 分别覆盖绑定、Wi-Fi 读取、同班多人打卡、重复提交、未连接 Wi-Fi、未登记 BSSID、错店、正常班、加班和跨午夜班次。
- 在测试库并发提交同一员工班次的同一种打卡，确认只有一条记录。确认员工离职、账号停用和非公开排班均无法打卡，且已有打卡的排班无法直接删除。
- 更换同一 SSID 下的不同接入点，确认每个实际 BSSID 都需登记；用未登记热点和伪造请求确认服务端按排班门店拒绝。
- 换绑审批和照片抽查留待后续。准备真实员工试点前配置入口限流并验证隐私声明。

停止试点时移除门店工作台内的 BSSID 配置并收回相关授权。已有打卡记录保留供核对。

## Web 端任务权限与联调准备

在隔离测试库应用本分支的迁移，再用「账号与角色」按实际职责配置以下权限。迁移仅注册权限点。员工账号从有效岗位取得相应权限；门店岗位的权限只对该岗位对应门店生效，并受账号指定门店范围限制。

| 权限点                    | 可操作内容                                             |
| ------------------------- | ------------------------------------------------------ |
| `operational-task:manage` | 管理授权门店的派发、循环模板、提交复核、整改及任务照片 |
| `operational-task:report` | 查看授权门店的完成统计                                 |
| `operational-task:export` | 导出同时具备统计权限的门店任务明细                     |

准备至少两个门店及独立的测试账号。授权后重新登录刷新菜单。测试恢复后，在 Web 端逐项验证：

- A 店管理账号只能向 A 店派发、复核和读取附件。员工在 B 店拥有普通岗位时，A 店管理权限不扩展到 B 店。
- 仅有统计权限的账号可以查询，CSV 直链接口返回拒绝；只有导出权限的账号同样不能导出。若统计覆盖 A、B，导出仅覆盖 A，选择 A 可导出，选择 B 或全部均被拒绝。
- 在账号列表修改 A 店账号的门店范围，比较「有效权限」和「授权记录」中的变化，再用旧会话请求 A、B 两店的考勤和任务接口。调整岗位模板角色后核对授权记录中的前后角色。
- 月度考勤 CSV 使用排班日统计。用跨午夜班次、补卡记录和缺少打卡的班次核对明细，并分别用只有查看权限、只有导出权限和两者兼有的账号请求导出。
- 在清单中记录异常并从对应检查项发起整改，核对原检查项、异常说明和提交时间。先打回并再次提交原任务，再用旧提交轮次发起整改，确认服务端拒绝。
- 向具备任务管理权限的账号抄送，再移除其中一家目标门店的权限，确认该店消息不再可见。释放认领时保留原截止时间，并验证旧认领请求无法覆盖新认领人。
- 撤销权限后，用旧会话直接请求派发、复核、附件、统计和导出接口，确认服务端重新核验。补卡审批同时验证本店授权和禁止自审。
- 用门店管理账号为逾期未提交任务申请补交。核对跨店申请、重复申请、总部自审和已停业门店的通过操作均受限制。通过后原任务重新开放，原认领与截止时间保存在申请历史。
- 以不同账号并发认领同一任务，确认只成功一次。打回后保留旧提交和照片；用旧提交版本请求复核会被拒绝。
- 在启用后台任务的测试环境模拟重复扫描同一循环模板，核对每个计划时间只生成一项任务。禁用 `BACKGROUND_JOBS_ENABLED` 可停止后台派发，已生成任务保留。

Web 端联调使用隔离环境的运营系统测试账号。运营任务链路可独立验收。真机 Wi-Fi 读取和打卡需要独立小程序 AppID、HTTPS 测试 API 和门店试点环境。

## 发布准备

- 在私有 V2 仓库的最新 `main` 上审查恢复补丁。上线前从生产发布记录核对当前应用提交及上一版本产物，从 `_prisma_migrations` 只读核对迁移名、校验和和完成状态。隔离空库已通过 63 个迁移，生产增量以实际盘点为准。若生产已经应用了前 46 个相同迁移，预计从 `20261109100000` 至 `20261110170000` 的 17 个迁移待应用。
- 在独立 MySQL 上恢复可用的备份并按实际迁移清单演练。确认业务表、考勤和任务权限、照片、审计记录及旧版应用兼容性，并记录恢复耗时。生产备份需要覆盖迁移前数据与可用于按时间点恢复的日志，并记录恢复位置。备份路径及连接配置仅存放在部署环境。
- 取得上线指令后先发布 Web 和 API，以一个营业门店及指定岗位配置权限和 BSSID。用测试账号核对任务流、权限回收、考勤查询和日志，再用独立小程序真机验收。
- 出现异常时先暂停循环模板、移除试点门店 BSSID 并收回试点授权。若要回退应用，使用事前验证可兼容新 schema 的上一版本产物，并保留已写入的考勤和任务记录。若迁移失败，检查已应用步骤及迁移日志，按演练结果修复或从迁移前备份恢复。生产数据库恢复前先确认写入停点与迁移后数据的保留方案。
